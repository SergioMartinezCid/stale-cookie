## Decision rationale (dated)

- **Site settings out of scope for good** (2026-08-07): Firefox's `browsingData` schema has no `siteSettings` at all (passing it is a validation error); not pursued on Chrome either.
- **"Visit memory" removed** (2026-08-07): the extension does not retain visit timestamps after deleting history — deleting history should delete that metadata too. The action log records what was deleted, not when sites were visited. The one config where deleted history leaves cookies looking "never visited" (cookie threshold > history threshold) gets a warning on the options page instead.
- **Undo scope** (2026-08-08): cookies only. History undo is out of scope for good (it would retain visit data after deletion — the rejected visit memory); download entries cannot be re-created via the API. Preview remains the primary safety mechanism.
- **Action/error log export = one JSONL file** (2026-08-08). Low priority — no major support commitment is planned for the extension.
- **Error log session-scoped, never persisted** (2026-08-08): errors exist so the user can attach diagnostics to a bug report by hand, not as a record the extension keeps. Anonymize option defaults ON because the data (domains, URLs) is personal.
- **Default thresholds**: cookies 90 days (conservative — deleting cookies logs people out), history 180 days (deleted history is unrecoverable, so it lives longer), downloads 90 days. History cleaning ON by default (its permission is install-time anyway); downloads OFF until enabled (optional permission).
- **Popup auto-scans on open only when a reminder is due** (2026-08-09), with a context banner.
- **Options "Saved" feedback is a fixed corner toast** (2026-08-09).
- **Icon** (2026-08-09): cookie-as-clock-face — the crumbling-cookie alternative was rejected as already common among extensions. **No `theme_icons`**: the theme-dependent light-outline swap made the toolbar icon differ from the add-ons list, which read as inconsistent; one variant everywhere.
- **MV2/MV3 split: no split** (2026-08-13): Firefox MV3 (event page, strict_min_version 142) was proven by the real-time verifications, so an MV2 Firefox build would solve nothing. One shared JS bundle; only the manifest differs per target.
- **Theme setting** (2026-08-14, user decision): dark/light selector in an options "Appearance" section, default dark — extension pages no longer follow the browser/OS theme.
- **Version 1.0.0 and keeping the GitHub links** (2026-08-14, user decisions): the repo must be made public before AMO submission or `homepage_url` 404s.
- **Action-log retention: 30-day age bound** (2026-08-15, user decision): the log stores deletion timestamps + site domains, which otherwise outlive the data they describe — a permanent residue of past sites, against the spirit of the rejected visit memory. `pruneActionLog` in `core/logs.ts` (age bound first, 200-entry cap second), enforced on every append and in the background's `onStartup` (idle profiles never append). Trade-off accepted: no audit trail older than 30 days. The 30 days is stated in `optionsLogsHint` (EN+ES), PRIVACY.md, and the README — keep them in sync with `ACTION_LOG_MAX_AGE_MS`.
- **`strict_min_version` lowered 142 → 140** (2026-08-15): 142 was only the version the real-time verification happened to run on, not an API floor. The true floor is 140 — `data_collection_permissions` in the gecko block (older Firefox refuses the key); everything else sits lower (`light-dark()` 120, `storage.session` 115). 140 covers the ESR audience. Verified empirically: full Firefox integration suite green against a Firefox ESR 140.0 tarball via the harness's new `FIREFOX_BIN` override. Accepted trade-off: one `web-ext lint` warning (Firefox for Android only got `data_collection_permissions` in 142) — irrelevant because the extension is desktop-only (`history` permission), and silencing it via a `gecko_android` key would wrongly declare Android compatibility on AMO.

## Implementation notes

Detail recorded when built; the code is authoritative.

- **Reminder**: exact `alarms` alarm at `reminderBase + reminderDays` (`reminderBase` in `storage.local` = install, last clean, or last skip). Badge = `action.setBadgeText('!')`, red. Notification (optional permission, requested from the options page) fires once per cycle (`reminderNotifiedAt` guard) so browser restarts don't re-notify; the badge does reappear on restart until cleaned/skipped. The popup shows "Skip this reminder" only while due. Defaults: reminder on, badge on, notification off, 30 days.
- **Automatic cleaning**: `autoCleanEnabled` (default off), interval default 7 days; exact alarm at `autoCleanBase + interval`; `autoCleanBase` cleared on disable so re-enabling starts a fresh cycle instead of cleaning immediately. Selection logic is `selectForAutoClean` in core (unit-tested). Each run resets the reminder base; while enabled the manual reminder is suppressed and its options controls grayed out.
- **Config import/export**: versioned envelope (`{version: 1, settings}`). Import is tolerant: envelope must match, individual fields validated by type/range with fallback to defaults; whitelist entries re-normalized to eTLD+1, deduped, sorted (`serializeSettings`/`parseSettingsImport` in `core/settings.ts`; the `Settings` type and defaults live in core, `ext/settings.ts` re-exports). Permission-gated flags (`clearDownloads`, `reminderNotification`) are turned off on import when the optional permission is missing — permissions can't travel in a file. Only config is exported; per-profile state (reminder/auto-clean bases, action log) stays put. `theme` travels in the export and falls back to dark on invalid values.
- **Logs viewer/export**: options "Logs" section lists both logs and exports one JSONL file (meta line with extension version + `anonymized` flag, then tagged `action`/`error` lines). Error log capture: global `error`/`unhandledrejection` listeners in all three contexts (`installErrorCapture` in `ext/errorLog.ts` — recording never throws), plus explicit popup catches so a failed scan/delete shows a status message instead of a stuck spinner. Anonymizer: per-export in-memory map gives each site (eTLD+1, subdomains folded) a consistent `site-N.example` pseudonym shared across both logs; URLs in error text collapse to `scheme://site-N.example/…` (paths/queries dropped); bare domain tokens validated with tldts `parse()` requiring an ICANN/private suffix (`getDomain` alone accepts unknown suffixes — it would flag `popup.js`); IPv4s pseudonymized; `moz-extension://<uuid>` / `chrome-extension://<32×a-p id>` origins become `…://extension` with the code path kept. Pure logic in `core/logs.ts` (unit-tested).
- **Undo/snapshot**: `deleteGroups` snapshots full cookie objects to `storage.session` before removing (manual and automatic share that path); single level — each cookie-including deletion replaces the snapshot, cookie-less deletions leave it alone; `SNAPSHOT_TTL_MS` (24 h) checked on read. Popup shows "Restore deleted cookies (N)" whenever a snapshot exists, including on open, so a no-preview automatic clean is undoable too. Restore rebuilds via `cookies.set` (`cookieRestoreDetails` in `core/restore.ts`, pure + unit-tested: hostOnly/domain handling, session vs `expirationDate`, expired-since-snapshot skipped, container store / firstPartyDomain / partitionKey pass through); one failing cookie never aborts the rest; a `restore-cookies` action-log entry is written; the reminder timer is untouched. Restored stale cookies reappear as stale in the next scan — expected. `RestorableCookie` extends `ScannableCookie` with optional fields so no generics ripple through core.
- **UI pass** (2026-08-09, from a 4-lens agent brainstorm: visual / UX flow / platform fit / a11y+i18n): shared tokens in `src/ui/theme.css` (Photon-adjacent palette via `light-dark()`; rem type scale with a 0.75rem floor; button hierarchy — unclassed buttons are secondary, `.primary`/`.danger`/`.quiet` explicit; `.sr-only` utility). Popup: `#toast` live region that post-action rescans cannot wipe; `#status` carries scan state and is the focus target after re-renders; inline delete confirm gets focus-in/Escape/focus-return; all-clean scans hide empty sections + footer; per-section select-all with indeterminate state; delete button counts items AND sites; hand-tuned selections survive rescans via an override map by domain; Protect confirms in the toast with inline Undo; the undo button states deletion time + expiry. Container badges tinted with the container's own `colorCode` (`ScanOutcome.containers`); partitioned badge neutral with an sr-only tooltip twin. Options: global clear LAST inside a danger-zone card; whitelist/days inputs show visible+announced errors (invalid values kept + `aria-invalid`, not reverted); import `confirm()`s before overwriting (names the whitelist size); global-clear `confirm()` names the selected types and the button disables while running; logs re-render on `storage.onChanged`; days inputs named via `aria-labelledby`; log lists are focusable scroll regions; error stacks are `<details>`.
- **Theme mechanism** (2026-08-14): `applyTheme` in `src/ui/theme.ts` forces `color-scheme` on the root element, which re-resolves every `light-dark()` token (no per-theme stylesheets); theme.css declares `color-scheme: dark` as the pre-JS state so the default renders without a flash. Options re-themes live on change; the popup applies the setting on open.
- **Background deletion** (2026-08-14, review finding): the popup used to run `deleteGroups` itself; popup pages are torn down on any outside click, which killed a long deletion mid-run, half done and unlogged. Now the popup sends `DeleteGroupsRequest` (`ext/scanner.ts`) and only renders the outcome; the background handler resets the reminder cycle when something was removed. Same finding hardened `deleteGroups` (per-group try/catch recording to the error log, partial counts always reach the action log) and `runAutoClean` (next alarm rescheduled in a `finally` — a mid-run throw used to kill scheduled cleaning until restart).
- **Chrome port** (2026-08-13): `minimum_chrome_version: 123` is floored by theme.css's `light-dark()`; the cookies `partitionKey` filter needs 119, `storage.session` 102. The error capture's bare `addEventListener` works in the service worker. Chrome integration suite: headless Chrome for Testing via Selenium Manager with `--load-extension`; the unpacked extension id is discovered from the service worker's DevTools target (`Target.getTargets`); `inExtensionPage` shims `browser = globalThis.browser ?? chrome` (Chrome MV3 `chrome.*` is promise-based). Because Chrome's `history.addUrl` can't backdate visits, the Chrome test seeds visits now and writes sub-second thresholds directly to storage.
- **Firefox integration harness** (2026-08-08): selenium-webdriver drives headless Linux Firefox (headless sidesteps the WSLg problems); geckodriver fetched by Selenium Manager, fresh throwaway profile per session, deleted on quit. `dist/` installs as a temporary add-on (selenium zips it); the extension UUID is pinned via the `extensions.webextensions.uuids` pref so tests navigate straight to `moz-extension://` pages. Seeding/verification run via `browser.*` from the extension's own pages through `executeAsyncScript` (same approach as `scripts/seed-dev-data.js`); Firefox's `history.addUrl` accepts a backdated `visitTime`.
